# CNA Gamer Services control protocol v1

This service and its accounts, assets and protocol are CNA-owned. There is no Xbox LIVE wire, account, binary or service compatibility. XNA objects never cross this protocol.

HTTPS POST `/cna/v1`, UTF-8 JSON, no redirects. TLS >=1.2; clients verify trust chain and hostname. Explicit `--insecure-loopback` admits HTTP **only** on a numeric loopback listener. Production deployment never uses plain HTTP credentials. Request/response body <=65,536 bytes, header <=8192 bytes, nesting <=16, arrays/object fields <=256 (enforced before DOM container insertion), 128 concurrent connections, 10 second transport deadline. No request/body/token logging. A fixed two-thread listener, one serialized SQLite service transaction/query boundary. HTTP malformed/truncated/oversized bodies terminate before service mutation.

Request: `{"v":1,"id":"unique-request-id","game":"registered-title-id","op":"hello","args":{}}`, optional `token` for authenticated operations. Exactly these six top-level keys; unknown keys rejected. Identifiers: 1..64 ASCII letters/digits/`.`/`-`/`_`; gamertags 1..32. Passwords 8..256 UTF-8 bytes. Duplicate JSON keys and invalid UTF-8 rejected. JSON numbers are validated before conversion. Responses: `{"v":1,"id":"same-id","error":"OK","result":{...}}`. For an unparseable/invalid envelope, ID is empty. Deterministic codes: `MALFORMED_MESSAGE`, `LIMIT_EXCEEDED`, `UNSUPPORTED_VERSION`, `INVALID_ARGUMENT`, `INVALID_STATE`, `NOT_AUTHORIZED`, `NOT_SUPPORTED`, `SESSION_FULL`, `UNKNOWN_OPERATION`, `UNKNOWN_TITLE`, `AUTHENTICATION_FAILED`, `UNAUTHENTICATED`, `NOT_FOUND`, `CONFLICT`, `DUPLICATE_REQUEST`, `RATE_LIMITED`, `REMOVED_BY_HOST`, `INTERNAL_ERROR`. Internal errors contain no SQL/filesystem/credential details.

`hello`: returns selected `version`, implemented `capabilities`, `maxMessageBytes`. v1 is exact major negotiation; clients never proceed with a different version or missing capability. Unknown title may negotiate but cannot authenticate/access data. Unknown operations fail before auth/data mutation. Title registered by administrator, never generated from process identity. No password/token belongs in title config.

`auth.login`: args `username`, `password`; returns `identity`, random 256-bit opaque `token`, Unix-second `expires`. OpenSSL scrypt N=32768,r=8,p=1 with independent random salts; constant-time verifier comparison. Unknown username performs dummy derivation. Token hashes only are persisted, bound to user/title, expires after 1 hour. Max 32 live sessions/user; 10 login attempts/minute/server-derived IP; bounded rate map. `auth.logout` revokes its access/refresh family (schema-4 legacy tokens revoke individually). `revoke-user` admin revokes all user credentials. Access credential survives server restart. Negotiated `session-refresh` adds the separately hashed
rotating refresh credential described below; CNA pumps maintenance and resumes private POSIX credentials.

All non-hello requests consume a title-scoped ID persisted for 24h; repeats return DUPLICATE_REQUEST without repeating mutation. <=100,000 IDs/title/24h. Use random 128-bit client process prefix plus monotonic counter, never counters alone. No automatic mutation retry using a new ID. Reads can use a fresh ID. Award is itself idempotent. Request IDs for failures after validation are also consumed. Unauthorized token requests do not consume IDs.

`gamer.lookup`/`profile.get`: args `gamertag`; public identity/profile metadata incl userId, gamertag, displayName, motto, region, allowOnlineSessions, gamerScore, totalAchievements, titlesPlayed. A valid title credential is required. Score/earned totals computed from persistence; titlesPlayed counts the titles in which the account has presence, an earned achievement or a leaderboard row. There is no gamer zone or reputation.

`friends.add`/`friends.accept`/`friends.remove`: args `gamertag`; see mutual workflow below (capability `friend-requests`). `friends.list` returns <=256 snapshots with accepted/request flags and title-scoped presence. Online if an accepted friend has a non-expired session seen within 90s. For an accepted friend in the calling title, `joinable` is true when the friend is online in a live player-match session that admits joiners now (lobby, or join-in-progress allowed) with a public slot free; `inviteReceivedFrom`/`inviteSentTo` report unexpired pending invitations between the two, and `inviteAccepted`/`inviteRejected` an unexpired invitation from the caller the friend accepted or dismissed. Each row also carries `away` and `busy` (false unless the friend is accepted and online). `presence.set`: integer mode 0..255 and text <=256 bytes, title-isolated. `profile.gameDefaults {}` / `profile.setGameDefaults {gameDefaults}` (capability `game-defaults`, schema 17) read and replace the caller's account-wide XNA `GameDefaults`: an object of at most `gameDifficulty` (`Easy`/`Normal`/`Hard`), `controllerSensitivity` (`Low`/`Medium`/`High`), `racingCameraAngle` (`Back`/`Front`/`Inside`), `primaryColor`/`secondaryColor` (`#rrggbb`) and the booleans `autoAim`, `autoCenter`, `moveWithRightThumbStick`, `invertYAxis`, `manualTransmission`, `accelerateWithButtons`, `brakeWithButtons` (anything else INVALID_ARGUMENT); both return `{gameDefaults}`. `presence.status {status}` (capability `presence-status`, schema 15) sets the caller's account-wide status, `online`, `away` or `busy`, which friends see as `away`/`busy` (XNA `FriendGamer.IsAway`/`IsBusy`); it is only ever what the player chose. There is no voice. Negotiated `auth.ping` heartbeat maintains authenticated activity; social push and general privacy
settings remain unfinished.

`achievements.list`: full title catalog <=128 (otherwise LIMIT_EXCEEDED); each key/name/description/howToEarn/score/display/picture/earnedTicks. Names <=128, descriptions/howToEarn <=1024, score 0..1000. Earned timestamps are .NET ticks from Unix conversion. `achievements.award`: args key; returns `awarded` (whether this call earned it) and the achievement's `name`; unknown key NOT_FOUND, duplicate award preserves original timestamp; user/title isolation via foreign keys. Picture is an immutable content hash, retrieved through negotiated assets capability.

Canonical parser/header/vectors live here. CNA copies protocol files with origin revision and runs byte comparison against this checkout. Add vectors when extending parser policy. SQLite migration version is separate from protocol major. Unknown future DB version refuses startup, never resets data.

## Reserved future boundaries (not implemented capabilities)

Server-push events will use separately correlated cursor/sequence stream with bounded retention and snapshot-on-gap. Control membership, title/session discovery and invitation tokens are separate from realtime game data. ENet stays SystemLink/realtime transport. Relay tickets scope to authenticated members/session/expiry, never reuse bearer credentials in unencrypted datagrams. Relay-first Internet path required before promising Internet sessions; direct endpoint hints alone do not solve NAT. Avatar description/catalog/hash-addressed GLB distribution travels as identity/resource metadata, never per-frame bones. Leaderboard writes flush at XNA gameplay boundaries with Ranked arbitration; arbitrary setters are not protocol persistence operations.

### Friends request model (v1 development revision)

`friends.add` requests friendship by `gamertag`; it does not grant private presence access.
`friends.accept` requires an incoming request and completes reciprocal account-global edges.
`friends.remove` cancels/rejects/removes both directions. Lists include pending incoming/outgoing
requests (`requestReceived`/`requestSent`) and mutually `accepted` relationships. Presence/online
are visible only for accepted friends. The graph is account-global; presence text is title-scoped.
Maximum 256 relationship edges per account and 256 list entries; no voice/invite/privacy-setting
capability is implied. Explicit block/privacy administration remains unfinished. Existing development
one-direction rows are now requests; no released wire compatibility is claimed for old fixtures.

### Immutable resources (capability `assets`, database schema 2)

Administration imports original PNG or GLB bytes, computes SHA-256 and associates the hash with
one or more titles. PNG admission requires a valid signature/IHDR, dimensions 1..512 and <=512 KiB;
GLB admission checks version-2 header/declared length and <=16 MiB. Full decode validation remains
client/content-loader responsibility; headers alone do not establish usable geometry or image data.
`assets.read` args: 64 lowercase hex `hash`, nonnegative integer `offset`, `length` 1..12288. Response:
`hash`, `size` 1..16777216, MIME, matching `offset`, lowercase `hex` for exactly min(length,remaining)
bytes. Offset at/past end is invalid; absent/unauthorized hashes are NOT_FOUND. Resource authorized
if associated with current title or a public user-picture association; profile privacy policy remains
unfinished. Filesystem paths/URLs never accepted over wire. Responses obey normal 64-KiB envelope.
Repeated chunks must report same metadata, and clients verify final SHA-256. This bounded initial
chunk path is correct for pictures but is not an optimized large-avatar streaming transport.

`migrations/002_assets.sql` runs transactionally after schema 1, preserving identities/earned state;
future schema versions refuse startup. Asset blobs in SQLite are immutable and deduplicated by hash.


## Leaderboard reads (`leaderboard-reads`, schema migration 3)

Administration provisions `(game,key,mode)` with ascending/descending sort, best/latest aggregation,
arbitrated flag and at most 32 named scalar column types. Policy is immutable after creation;
runtime clients cannot create definitions or issue SQL. Trusted `seed-leaderboard` is development
administration, not gameplay submission. Session-authorized gameplay commits use the separately
negotiated `local-leaderboard-commit` capability below. Setter changes remain transient until commit.

`leaderboards.definition {key,mode}` returns policy and the column type map.
`leaderboards.read {key,mode,start,size,pivot?,gamers?}`: mode is signed 32-bit, start 0..Int32.MaxValue,
size 1..100, optional pivot is a gamertag <=32 UTF-8 bytes. `gamers` is an explicit restricted set
(up to 100 names); an empty set yields no rows. Absent set selects the full board. Returns start,
filtered total and entries `{userId,gamertag,rating,rank,columns}`. Rank is global one-based ordinal,
ties broken by stable user ID. Centering uses max(0, pivot filtered index - size/2), absent pivot
starts at top. Paging is a live database read; entries can change between pages (no snapshot token).

Rating is signed 64-bit. Columns are `{name:{type,value}}`, types int32/int64/single/double/string/
datetime/timespan/outcome/stream. Integers preserve all 64 bits; datetime is .NET ticks 0..3155378975999999999,
timespan signed ticks, outcome 0..3, string <=256 UTF-8 bytes; floats must be finite; stream (XNA
`GetValueStream`) is lowercase hex of at most 256 bytes. Column payload <=2 KiB. Request/response
still obey the 64 KiB envelope cap: a page with many large columns may return LIMIT_EXCEEDED; use a
smaller page. Time-window rotation, TrueSkill and exact Xbox validation/pivot policy measurements
remain open (Ranked arbitration: below).


## Local gameplay commits (`local-leaderboard-commit`, schema migration 4)

`leaderboards.game.begin {kind:"local",participants:[accessToken,...]}` authenticates 1..4 distinct
local online accounts, all bound to the request title. The request account must be a participant
and owns the returned random 128-bit `gameplay` epoch. Participant tokens are internal credentials
sent only over the authenticated control transport, never XNA API arguments or title manifest data.
No other kind is accepted yet; Ranked directory/arbitration is not implied. At most 16 uncommitted
epochs per owner, 24-hour lifetime; expired epochs/members are pruned. Negotiated `leaderboard-epoch-abort` releases abandoned epochs. Crash/offline interruptions
remain bounded by this lifetime/quota.

`leaderboards.game.commit {gameplay,entries:[{userId,key,mode,rating,columns},...]}` is owner/title
bound; every user must belong to the epoch, every board must be provisioned and nonarbitrated, and
all scalar column types/limits must match the catalog. At most 128 unique user/key/mode rows. All
rows validate before a single database transaction. Aggregation `latest` replaces rating/columns;
`best` replaces only a strictly better rating according to ascending/descending policy (equal
ratings preserve the earlier columns). These are CNA catalog policies, not a claim that all Xbox
aggregation configurations have been measured. The transaction persists entries and closes the
epoch with a SHA-256 digest of canonical entry JSON. A new request ID with an identical retry
returns OK, even after server restart; a different payload on a closed epoch returns INVALID_STATE.
The general duplicate request-ID rule still applies. Epoch membership conveys leaderboard write
authority only; it is not realtime connectivity or matchmaking session membership.

The client publishes a writer scope at the Playing update boundary. Host EndGame invokes final
nonarbitrated write handlers while still Playing, submits drafts, closes the scope, then raises
GameEnded at the Lobby boundary. Other service/network calls in the final handler are rejected.
A failed commit retains drafts and Playing state so EndGame can be retried. TrueSkill computation
remains unfinished (Ranked arbitration and the relay are described in their own sections). Early leaving fires the
final handler with IsLeaving=true, commits before discarding local identity, and closes the scope.


`leaderboards.game.abort {gameplay}` (capability `leaderboard-epoch-abort`) cancels only an
uncommitted epoch owned by the authenticated account/title. IDs must be 32 lowercase hex digits.
Unknown/already-removed IDs return OK; committed epochs return INVALID_STATE; a different owner
returns NOT_AUTHORIZED. Cascading member deletion releases the active-epoch quota immediately.
The client uses bounded queued cleanup when unpublished gameplay or a C++ destructor abandons
an epoch; it never calls game handlers from the destructor. A lost connection prevents best-effort
abort and the epoch then expires normally. This operation cannot erase committed leaderboard data.


## Ranked arbitration (`ranked-arbitration`, schema migration 10)

A Ranked directory's host update from Lobby to Playing opens an arbitration round that records the
exact member accounts and machines at that moment; the update back to Lobby closes it. Rounds have
no foreign key to the directory, so a round outlives a host that closes the session mid-game.

`leaderboards.game.commit` accepts an optional `arbitration:{session,revision}` object, where
`revision` is any directory revision the committing machine observed while Playing in that round.
With it, rows for boards defined `arbitrated` may name any round member account and together form
the report of the epoch owner's machine; without it, or for a non-member account, such rows are
NOT_AUTHORIZED. Nonarbitrated rows keep the epoch-membership rule (a machine writes only its own
gamers). Unknown/foreign rounds are NOT_FOUND. One report per machine and round: an identical replay
is OK, a different one INVALID_STATE. Nonarbitrated rows commit immediately as before.

Resolution happens when every round machine has reported, 60 seconds after the round ended, or one
day after it opened, whichever comes first; any commit sweeps up to eight due rounds of its title.
A `(user,key,mode)` row is written only when a strict majority of the machines that reported that
row sent an identical row (rating and columns); the board's aggregation policy then applies, and
anything else is discarded. Finishing machines report every gamer, so a machine that left early and
reported only its own gamers cannot overrule them, while their own rows do not depend on the
departed machine. Resolved rounds are pruned
after a day. This is CNA's documented policy for the XNA rule "arbitrated statistics are written by
all machines for all gamers"; it is not Xbox LIVE arbitration, and CNA computes no TrueSkill: a
title's skill board is an ordinary arbitrated board holding the values its machines agree on.

## Messages and player reviews (`messages`, `player-reviews`, schema migration 11)

Both are account-global social data, like the friends graph (any valid title credential may use
them). `messages.send {gamertags,text}` delivers `text` (<=256 UTF-8 bytes) to 1..100 distinct
existing accounts other than the sender; at most 200 messages per sender per hour (RATE_LIMITED)
and 100 stored per recipient (LIMIT_EXCEEDED), checked before any row is written.
`messages.list {start,limit}` (start 0..100, limit 1..32) returns `{start,total,unread,messages}`,
newest first, each `{message,sender,text,created,read}`. `messages.read {message}` marks and
`messages.delete {message}` removes one of the caller's own messages; any other ID is NOT_FOUND.

`reviews.submit {gamertag,rating}` records `prefer` or `avoid` feedback about another account, or
withdraws it with `clear` (at most 1,024 reviews per reviewer). A searcher's `sessions.find` never
returns sessions hosted by an account that searcher rated `avoid`; nothing else uses reviews yet.
These back the XNA Guide Messages/Compose Message/Player Review panes; they are CNA features, not
Xbox LIVE messaging or reputation.

## Avatars (`avatars`, schema migrations 12 and 14)

Each account has at most one avatar: a 1021-byte description in CNA's own encoding (see CNA
`docs/avatars.md`). Format 1: format byte 1, `CNA`, body type, height 1450..2050 mm, build,
catalog version, seven RGB colors, six 16-bit catalog item ids, zero reserved bytes, CRC-32 of
bytes 0..1016 in 1017..1020. Format 2 (byte 0 = 2) keeps bytes 1..42 and adds a facial-hair
feature item id (43..44) and sixteen face-shape bytes (45..60), reserved zero after that; it must
use at least one of them. It is not an Xbox LIVE avatar and carries no Xbox data.

- `avatars.get {userIds, formats?}` (1..16 hex identities; `formats` lists the description formats
  the caller reads, default `[1]`) returns `{avatars:[{userId,description,revision}]}` in request
  order; `description` is 2,042 lowercase hex characters, or null (revision 0) for an account
  without an avatar or an unknown identity. A format 2 avatar read by a caller that does not list
  format 2 is returned as its format 1 copy (facial hair and face shape dropped, everything else
  kept), which is itself a valid description. Any signed-in account may read any avatar, as it may
  read a gamertag.
- `avatars.set {description}` replaces the caller's own avatar and returns `{revision}`. The
  description must be a valid format 1 or 2 description whose catalog version was imported here,
  whose required slots (hair, top, bottom, shoes) are filled, whose every item exists in that
  catalog in that slot, and whose facial hair (format 2) is one of that catalog's feature items;
  anything else is INVALID_ARGUMENT. At most one change per two seconds (RATE_LIMITED).
- `avatars.catalog {version?}` returns `{version,manifest}` for the requested (or newest) imported
  catalog; NOT_FOUND if there is none. The manifest is CNA's `catalog.json`: rig, bodies, items
  (id, slot, per-body-type asset, optional CreateRandom weights, hair `hatAssets`, hat
  `coversHair`), optional `featureItems` (facial hair) and `faceControls`, face atlas layout,
  animations, and every file's name, SHA-256 and size.

Catalog files live in the immutable asset store and are read with `assets.read` by hash from any
title. Catalogs are imported by administration (`avatar-catalog <dir>`). Import refuses anything
a CNA client would refuse: every file's hash and size; every model against the avatar contract
(one embedded buffer, no URIs or required extensions, the 71-joint rig in XNA's topology with
identity bind rotations, skinned triangle lists with only position/normal/texcoord/joints/weights,
in-range indices, joints and weights, bounded counts, PNG textures of at most 1 MiB, CNA material
extras, cubic-spline joint animations with valid expression keys); every item fitted to its body's
rig; all 31 animation presets; a face atlas layout naming every expression state; bounded face
controls. A version never changes once imported, and a newer version keeps every earlier item id
(including feature items) in the same slot, so older descriptions stay valid. Administration also
sets accounts' avatars (`avatar <user> random [female|male] | set | clear`); random avatars follow
the newest catalog's weights and get a shaped face (format 2) when it has face controls.

## Rotating credentials (`session-refresh`, schema migration 5)

`auth.login` additionally returns `refreshToken` (random 256-bit opaque hex) and `refreshExpires`
(absolute Unix seconds, 30 days), plus `serverTime` at issuance. Clients schedule from the
remaining lifetime relative to this server time, rather than requiring matching clock offsets. The server stores only SHA-256 credential hashes and family
association, not persistent bearer plaintext. Up to 32 active families per account, across titles;
revoked/expired families and expired access records are pruned at issuance. Existing access tokens
from schema 4 continue to work until expiry/logout without a refresh family.

`auth.refresh {refreshToken}` requires the matching title and no access token. Both login and
refresh share the bounded 10/minute source throttle and general correlation/request-ID limits.
Successful refresh atomically marks the previous credential used, retires earlier family access,
and returns identity/new access/new refresh with the original absolute refresh expiry. New access
expires at min(now+1 hour, family expiry). Family rotation count <=1,024; no indefinite lifetime
extension. Old credential reuse revokes that family and all its access authority; unrelated
account/device/title families remain valid. Unknown, malformed, revoked, expired or wrong-title
credentials return UNAUTHENTICATED without revealing account state. Logout revokes its family;
`revoke-user` administration revokes every family plus schema-4 legacy access tokens.

`auth.ping {}` (capability `heartbeat`) requires access authentication and returns serverTime;
activity updates the same last_seen used by friends' online status. This is control/service
maintenance, not gameplay packet exchange or service push.

The model follows established [refresh rotation/replay guidance](https://www.rfc-editor.org/info/rfc9700/),
without claiming OAuth compatibility. A lost successful rotation response can require fresh Guide
sign-in: replay is rejected, not indefinitely accepted to hide an ambiguous transport failure.
CNA private POSIX user storage, Update maintenance and automatic service reconnect are tested.
Windows/browser credential persistence remains ephemeral pending secure platform providers.


## Session directory (`session-directory`, schema migration 6)

This capability is the logical control directory, not realtime connectivity, relay, XNA arbitration
or an assertion that CNA public PlayerMatch/Ranked APIs are implemented. No IP endpoint is returned.
The CNA frontend/relay integration remains GS-007b/GS-008. Never declare Join success solely because
membership was inserted. Authentication and local participant credentials use verified control TLS.
SystemLink does not use this directory.

`kind` is `player` or `ranked`, independent of XNA enum ordinals. `properties` is exactly eight
nullable signed-32-bit integers. Null search values are wildcards; a nonnull search value matches
only an equal advertised integer. Maximum session gamers 2..31, private slots 0..maxGamers.
Directory args require exactly the documented fields; unknown or missing fields are INVALID_ARGUMENT,
except `allowHostMigration`, which a client that predates `host-migration` leaves out.
These facts follow the existing XNA metadata/reference behavior; no managed/FNA code is used in the
MIT server. Ranked type selects a directory partition; Ranked arbitration/TrueSkill are unfinished.

`sessions.create {kind,maxGamers,privateSlots,properties,allowJoinInProgress,participants[,allowHostMigration]}`:
participants is 1..4 distinct access credentials, all current title/online-enabled, including the
request account. Server issues random 128-bit session/machine IDs and atomically inserts all local
users. Users cannot hold two active directory memberships for the same title. Host participants
consume public slots first, then private slots if needed. At most 1024 live sessions/title and
16/host/title. Directory mutations use prepared SQL, never caller paths/queries.

`sessions.find {kind,localCount,properties,start,limit}`: localCount 1..4, live offset start 0..1024,
limit 1..32. Returns bounded `sessions`, `start`, `more`. Results have enough public slots for all
requested locals, allow Lobby/join-in-progress, match properties/type/title and exclude the caller's
own membership. Stable order created/id; this is a live directory, not a frozen pagination snapshot.
Summary fields: session, kind, state, maxGamers, privateSlots, properties, allowJoinInProgress,
revision, hostId/hostGamertag/hostMachine, currentGamers, openPublicSlots/openPrivateSlots.

`sessions.join {session,participants}` validates every 1..4 local participant before atomically
adding a new machine. Ordinary discovery joins cannot consume private reservations (`SESSION_FULL`).
Playing joins require kind `player` and allowJoinInProgress. Ranked sessions never allow new
machine joins during gameplay, including accepted invitations. Repeating an already joined identical machine group is
idempotent with a fresh request ID; changed groups/other active memberships return INVALID_STATE.
Snapshot adds machine and members `{userId,gamertag,machine,privateSlot,ordinal}` (ordinal 0..30).
Machine IDs/ordinals are logical identifiers, not authentication secrets or realtime ENet peer IDs.

`sessions.get {session}` returns full snapshot only to members. `sessions.touch {session}` requires
that machine's authenticated owner, renews its 90-second lease and returns snapshot; host touch
also renews directory lifetime. Update clients should touch every 30 seconds. Expired remote machines
lose all local users atomically and advance revision. Host expiry removes the directory/membership,
unless host migration hands it over (below). A machine whose relay connection closes keeps its lease
for only 20 more seconds unless it reconnects (which restores the lease), so a crashed machine is
detected in about 20 seconds rather than 90.
Restart retains live directory state only inside the remaining lease; no automatic indefinite revival.

`sessions.update {session,revision,maxGamers,privateSlots,properties,state,allowJoinInProgress[,allowHostMigration]}`:
host only; revision compare-and-swap, stale revision CONFLICT. Lobby/Playing states only; capacity
cannot shrink below already allocated public/private membership. Every accepted membership/state/
property change increments revision, which is bounded signed-32-bit; exhausted revisions close the
session deterministically. Host update renews host lease. XNA EndGame will map Playing to Lobby,
not to deleting the directory. EndGame leaderboard commit/arbitration ordering remains CNA integration.

`sessions.remove {session,machine}` (`session-removal`, schema migration 13) is XNA's
`NetworkMachine.RemoveFromSession`: only the host machine's owner, never its own machine
(INVALID_ARGUMENT), a 32-hex machine of that session (else NOT_FOUND). It removes that machine and all
its local users, records them as removed for the session's lifetime and advances revision; the result
is the host's snapshot. A removed user's `sessions.get`/`touch`/`leave` and `sessions.relayTicket`
answer REMOVED_BY_HOST instead of NOT_AUTHORIZED, so the client ends its session for that reason; the
relay closes the machine's channels as for any membership loss.

`sessions.leave {session}` requires machine owner, removes all that machine's local users and advances
revision. Host leave ends the directory and removes every member (`ended:true`), unless host migration
hands it over (`ended:false`). Nonmember/wrong-title/expired resources
fail deterministically. Explicit logout/revocation prevents further authenticated calls; directory
leases bound interruption cleanup to 90 seconds. Invitations/private joins are a separate capability below; server push remains unfinished. No Internet realtime multiplayer evidence is implied by these unit tests.


## Host migration (`host-migration`, schema migration 16)

XNA's `NetworkSession.AllowHostMigration`. `sessions.create` and `sessions.update` take an optional
boolean `allowHostMigration` (update without it keeps the current value). Member snapshots
(create/join/get/touch/update/remove) carry `allowHostMigration: true` only while it is set; search
results never do, so clients that predate the field read every session they could read before.

When it is set and the host machine leaves (`sessions.leave`) or its lease lapses (a crash, detected
through the relay as above), the service makes the machine holding the lowest remaining member
ordinal the host: `hostMachine` and `hostId`/`hostGamertag` (that machine's owner) change, the old
host's users leave, the revision advances and the session's lease restarts. Every other member and
ordinal is unchanged. With no other live machine, or without the flag, the session ends as before.
The choice is the service's alone; clients follow the snapshot. Ranked arbitration rounds are
unaffected (they record members and machines, not the host).

## Adding local gamers (`session-add-members`)

XNA's `NetworkSession.AddLocalGamer`. `sessions.addMembers {session,participants}`: only a machine's
owner; `participants` are 1..3 access credentials of the new local accounts (current, title,
online-enabled, not the owner, not in any live session of the title). The machine may hold at
most four users (LIMIT_EXCEEDED). The new users take public slots only (SESSION_FULL) and are
refused while a Ranked session, or a PlayerMatch session without join-in-progress, is playing
(INVALID_STATE). Each gets the lowest free ordinal; the revision advances and the result is the
owner's snapshot. The machine's next relay ticket names the whole grown group, and a relay grant
already held stays valid while every member it names still belongs to the machine.

## Session invitations (`session-invitations`, schema migration 7)

These are independent CNA control semantics, not Xbox LIVE accounts/protocol or evidence that the
public XNA Guide/InviteAccepted path is wired. Receipt, explicit acceptance and joining are distinct.
The server advertises polling inbox operations; no invitation push is claimed. A future control
push channel must deliver receipt without fabricating acceptance. Both directory kinds support
these controls; Xbox Ranked invitation/arbitration rules require separate frontend behavioral work.

All argument sets are exact; unknown/missing fields are INVALID_ARGUMENT. Invite/session IDs are
32 lowercase hex characters (128-bit random IDs). An invite ID is not a bearer credential: title-
bound authentication plus the designated recipient is required for inspection/acceptance/join.
Send requires active session membership and online privilege; any active local member may send.
No unmeasured friends-only restriction is imposed. Recipient must exist, be online-enabled and
not already belong to that session. Offline accounts can receive persistent invitations.

`invites.send {session,gamertag}` returns `{invite,session,senderId,senderGamertag,status,created,
expires,acceptedAt,kind}`. Initial status pending, acceptedAt=0. Duplicate pending/accepted sends
for that sender/session/recipient return the same ID and original expiry. TTL is 900 seconds,
subject to the session's separately renewed 90-second host lease. Closing/expiring a host cascades
all of its invitation authority. Send does not grant or reserve membership/capacity.

`invites.list {start,limit}` returns `{invites,start,more}` for the authenticated recipient/title;
only pending/accepted, unexpired and live-session rows, ordered created/id. start 0..64, limit 1..32.
`invites.get {invite}` inspects only that recipient's row. `invites.accept {invite}` moves pending to
accepted and sets acceptedAt; repeating acceptance retains the same time. `invites.dismiss {invite}`
moves pending/accepted to dismissed, idempotent for dismissed. Used/dismissed cannot be accepted;
used cannot be dismissed. Receipt/list/get never changes acceptance. Expired rows return INVALID_STATE,
unknown/closed/wrong-title NOT_FOUND, another recipient NOT_AUTHORIZED.

`sessions.joinInvited {session,invite,participants}` requires accepted/unexpired invite for that
session/title and the request account, plus 1..4 authenticated distinct title accounts including the
recipient. Allocate private slots first then public atomically; insufficient total capacity is
SESSION_FULL with invitation/membership unchanged. Playing joins still require kind `player` and allowJoinInProgress; Ranked gameplay refuses
new invited membership with INVALID_STATE without consuming the invitation.
A successful membership transaction marks used and records the machine. Repeating with a fresh
request ID succeeds only for that exact already-joined machine/group; changed groups, leaving then
replaying or trying another account fail. Acceptance alone does not promise the session can still
be joined. No realtime endpoint, relay ticket or ENet payload is encoded in these operations.

Limits: 64 live incoming per recipient/title, 16,384 retained rows/title and 32 new sends per
sender/title in an hour-long window beginning with its first send. Duplicate sends consume no
additional quota. Dismissal, restart and session close/recreate cannot reset the independent
persistent sender counter. LIMIT_EXCEEDED or RATE_LIMITED occurs before mutation. Old records are
trimmed after one day; session cascade can remove them sooner while preserving abuse counters.
All mutations use prepared statements/transactions; callers supply no filesystem/query strings.

### Relay authority foundation (schema 8; data transport pending)

Negotiated `relay-tickets` implements `sessions.relayTicket` for an owning machine's complete
authenticated local group. It does not advertise working relay forwarding. See
[separate realtime protocol](relay-v1.md) for exact request/result, one-use redemption, revocable
family-bound grants, resource limits and remaining WSS transport work. This is CNA authority,
not Xbox LIVE tokens or wire compatibility. No ticket may appear in URLs or logs.

### Ranked lobby policy (schema migration 9)

For kind `ranked`, allowJoinInProgress must be false. Create/update attempts to enable it
return INVALID_ARGUMENT without mutation. Gameplay directories hide Ranked sessions and new
ordinary/invited joins return INVALID_STATE even for a legacy invalid true flag. Replaying an
already-present identical account group remains idempotent; it does not admit new players.
Migration 9 repairs prior true flags, increments their revision within the existing integer
ceiling and preserves membership. This is a CNA functional policy inspired by the XNA Ranked
contract; no Xbox LIVE certification/account/wire compatibility is implied.
